# Zephyr IDE 工作台布局设计

**评审稿 · 建议方案**　进入 Zephyr 活动时，在编辑区呈现一个「Zephyr IDE」工作台。用户选好工程和构建目标后，可以在同一处看依赖、配环境、启动构建。顶栏只回答两件事：现在操作哪个工程，以及可以切到哪里。内容放得下时，菜单、展示页和清单都没有滚动条。

## 一次打开，在哪里完成工作

当前分支已经让七个配置入口共用一个编辑器面板，但导航仍平铺「设置、概览、主机工具、SDK、工作区、west Git 模块、运行器配置」。例如，用户为一个工程准备构建时，要自己判断模块在工作区、编译器在 SDK、下载工具又在主机工具。建议按正在做的事合并入口，同时保留现有命令直达对应位置。[当前面板](../../src/panels/configuration-page.ts) · [当前导航](../../src/panels/configuration-navigation.ts)

| 工作台位置 | 放什么 | 为什么在这里 |
| --- | --- | --- |
| 项目配置（进入时默认） | 选择工作区、工程、构建配置；核对目标板、依赖和目标版本；构建、烧录、调试 | 同一工程可以有多个构建配置，烧录器也属于具体构建。换目标应能立即看见变化的依赖和操作。[仓库工程指南](../src/content/docs/user-guide/project-setup.md) |
| 工具环境 | 主机工具、Python、SDK 或外部工具链、探针工具。选中一项就在原位查看来源、版本与路径 | 工具通常跨工程复用。工程页可以直接跳到缺失的那项，处理完返回原构建配置。[Zephyr SDK](https://docs.zephyrproject.org/latest/develop/toolchains/zephyr_sdk.html) |
| 扩展设置 | 用户和工作区偏好，如语言相关显示、状态栏和默认操作 | 这些设置的作用范围比一个工程大，单独放置可以避免误改其他工程。 |

侧栏保留可折叠的工作区和工程对象树；编辑区内也能选择对象，侧栏收起后仍可完整操作。原「概览」中的就绪状态放进项目配置，「工作区」和「west 模块」归入当前工作区，「运行器配置」从当前构建的烧录或调试动作进入。工作区级同步应明确标出影响的工作区，即使入口来自某个工程。

配置首页按当前上下文提供一个起点。已有工程时恢复上次的工程和构建配置；有工作区但没有工程时就地显示「选择工程」和「从示例创建」；首次使用可直接打开本地工程或定位已有环境。从其他活动切回 Zephyr 时显示配置工作台。点击对象、切换功能或重复打开命令只定位这一个面板。扩展只管理自己的内容，VS Code 的代码标签栏仍由用户控制。[VS Code 视图指南](https://code.visualstudio.com/api/ux-guidelines/views) · [Webview 指南](https://code.visualstudio.com/api/ux-guidelines/webviews)

## 展开终端时，界面是什么样

下面是「项目配置 → 模块」的中间编辑区。工程上下文和功能导航始终在同一位置。两个清单上下排列，标题、计数和批量操作位于各自清单的滚动区外。

```text
 Zephyr IDE                                             ← 唯一的扩展编辑器标签
 ─────────────────────────────────────────────────────────────────────────
 项目配置   工具环境   扩展设置
 工作区 ▾   工程 blinky ▾   构建配置 板 A / debug ▾               [构建]
 ─────────────────────────────────────────────────────────────────────────
 构建配置   模块   烧录与调试
 [按模块名搜索_________________]                         [添加仓库] [更多]
 已勾选 2                                             [下载 / 更新所选]
 ─────────────────────────────────────────────────────────────────────────
 ☑ 模块 A    由当前板配置引入      ✓ 与清单一致    目标版本 …      [更新]
 ☑ 模块 B    模块 A 声明依赖       ↓ 未下载        目标版本 …      [下载]

 待选 12
 ─────────────────────────────────────────────────────────────────────────
 ☐ 模块 C    工作区清单            △ 版本不一致    目标版本 …      [更新]
 ☐ 模块 D    工作区清单            ↓ 未下载        目标版本 …      [下载]
 ─────────────────────────────────────────────────────────────────────────
 VS Code 终端    west build …                           ← 原生底部面板
```

| 空间变化 | 布局反应 |
| --- | --- |
| 清单只有两行，或展示页只有几个字段 | 随内容收紧，剩余空间留给工作区。整页和清单均不显示滚动条，也不预留空轨道。 |
| 待选有 80 项，已选只有 2 项 | 已选占两行的自然高度，余量给待选。仅待选列表可滚动，滚动到底仍能看见已选和批量下载。两个列表都很长时分别限高、独立滚动。 |
| 打开右侧聊天，编辑区变窄 | 用当前工程和目标简称显示上下文；行内版本和依赖来源可折到第二行；编辑、移除等次要动作收入「更多」。搜索、单项下载和批量下载仍可见。一级导航在极窄时变为一个带当前名称的菜单。 |
| 拉高终端，或使用大字号 | 先收起说明和次要字段，长表单按任务分组原位切换。仍装不下时，只让当前详情正文按需滚动；键盘可以到达最后一项并返回。 |

尺寸以编辑区的实际可用宽高为准。布局以窗口高度分配导航、上下文和内容区；可收缩的列表区只在内容确实溢出时使用 `overflow: auto`。短展示页不设凑满屏幕的最小高度，不靠隐藏滚动条裁掉内容。分区用主题边框和间距，选中态用文字与标记；一致、缺失、版本不同分别配合主题色、图标和中英文状态词。浅色、深色和高对比主题都应可读。[VS Code Webview 指南](https://code.visualstudio.com/api/ux-guidelines/webviews)

**值得分开的内容只有需要并排工作或持续观察的内容。** 点击「查看声明」用原生编辑器打开对应的清单、Kconfig 或板文件；构建输出进入终端，问题进入 Problems，调试使用 VS Code 的调试视图。切换这些内容后，返回工作台能回到同一工程、选项和列表位置。路径选择使用文件选择框，短设置用原位详情，均无需再开一个配置标签。

## 自动识别依据什么

工程、板和构建配置共同决定本次需要什么；工作区清单决定某个仓库应取哪个版本。工作台应同时显示这两类依据。west 清单中的仓库可以是工具，已检出的模块也可以由用户通过本地路径提供。仅凭仓库名相似或存在于清单，无法断定当前工程一定依赖它。[Zephyr 模块与 west 项目](https://docs.zephyrproject.org/latest/develop/modules.html) · [west 清单](https://docs.zephyrproject.org/latest/develop/west/manifest.html)

| 从哪里读取 | 识别结果及显示方式 |
| --- | --- |
| 当前 west 工作区及其有效清单 | 用 west 解析清单位置、导入、项目路径和目标 revision；在当前工作区内比较本地检出和目标。分支或标签未能解析时显示「目标版本待确认」。[west 工作区](https://docs.zephyrproject.org/latest/develop/west/workspaces.html) |
| 当前应用、板目标、配置片段和 overlay | 通过当前 Zephyr 版本的配置流程识别板、限定符和实际生效的配置。来自构建目录的结果须与当前应用、板和配置对应；切换目标后重新确认。多镜像构建保留各镜像的依赖来源。[Zephyr 应用开发](https://docs.zephyrproject.org/latest/develop/application/index.html) · [构建、烧录与调试](https://docs.zephyrproject.org/latest/develop/west/build-flash-debug.html) |
| Zephyr 模块声明、显式本地模块和本次构建证据 | 沿已确认的直接依赖追踪传递依赖，显示「由谁引入」、声明文件和清单目标版本。新工程还没有构建结果时，先选能证明的项；条件未求值的项显示「待配置确认」。解析使用相应格式的工具或解析器，允许换行、空行、多个空格和制表符等该格式接受的写法。[Zephyr 模块](https://docs.zephyrproject.org/latest/develop/modules.html) |

例如选择 HC32F4A0 工程，如果当前板配置与该版本 Zephyr 的声明能证明需要 `cmsis_6` 和 `hal_xhsc`，两项自动进入「已勾选」，各自显示来源。旧 `cmsis` 只有在本次配置也声明需要，或用户手动选中时才出现于已选区。切换构建后撤销仅属于旧目标的自动选择，保留可辨认的手动选择。自动识别可直接复用仓库已有的[依赖分析](../../resources/west_dependencies.py)和[模块选择器](../../src/panels/workspace_panel/components/west-project-picker.ts)。

## 可以散装，也可以完整离线

工具环境按组件列出「使用位置、检测到的版本、来源、验证结果」。每项可独立选择系统已有工具、指定文件或目录、导入本地包，或从官方源与自定义镜像获取。只显示该组件支持的方式。选定来源后先在本机验证；显式指定的位置失效时显示原位置和「重新定位」，避免无声换用另一个版本。仓库已有外部环境入口，可沿用。[外部环境指南](../src/content/docs/getting-started/external-environments.md)

| 组件 | 本地来源与验证 | 在线动作 |
| --- | --- | --- |
| SDK 或外部工具链 | 选择已有安装目录或兼容的本地包，核对宿主系统、架构和目标编译器。最小 SDK 还缺目标工具链时列出具体包。安装脚本需要额外下载的步骤在离线模式下提前提示。[Zephyr SDK](https://docs.zephyrproject.org/latest/develop/toolchains/zephyr_sdk.html) | 用户选择版本以及官方源或镜像后下载。 |
| Python、west、CMake、Ninja、Git | 可分别选已有可执行文件；Python 包可来自本地 wheel 目录。在选中的解释器环境中验证实际需要的包和版本。 | 按缺失项安装，可指定包源。 |
| west 仓库、二进制组件 | 仓库可以来自已有检出或包含目标提交的本地 Git 镜像；普通源码包可作为本地模块，单独标明版本验证能力。二进制组件按模块声明独立核对文件与摘要。[Zephyr 模块](https://docs.zephyrproject.org/latest/develop/modules.html) | 单项或多选同步到清单版本；二进制组件按需获取。 |
| 烧录与调试工具 | 按当前构建可用的 runner 定位探针工具；缺少该工具只影响相应烧录或调试动作。 | 需要安装时可选择供应商来源或自行指定安装位置。 |

**离线是可验证的操作模式。** 打开工作台、切换工程、刷新本地状态都只读取本机。已有 SDK、Python 环境与模块时，可以直接配置和构建；如果只有本地镜像，同步前先验证所需提交是否存在。一个本地提交与固定清单版本一致，可以直接显示「与清单一致」；远端分支的新旧另列「未检查」或上次检查时间。缺少文件时指向该组件的本地包选择器。启用联网后，用户也可以只下载这一项。

工程内路径以对应工作区或工程为基准；用户指定的外置 SDK、工具可执行文件、离线包目录属于当前机器，存入本机设置。共享配置保留相对路径或所需版本。Windows 和 Linux 可以用不同的工具位置打开同一个工程。

## 界面合并后，各功能如何保持独立

工作台外壳只持有「当前工作区、工程、构建配置、所选功能」和导航状态。每个功能从自己的输入读取状态，拥有自己的验证和操作入口；页面复用已有命令。依赖识别只给出建议及理由，下载由同步动作触发。工具定位只给出本机可用能力，构建和烧录分别取自己需要的能力。任务结果带回所属工作区和构建标识，避免旧任务完成后改写新工程的画面。

例如，将 Python 指向已有虚拟环境、SDK 指向解包目录、模块指向本地 Git 镜像后，工程即可验证构建条件。此时即使某个探针工具缺失，也只需在点击「烧录」时处理这一项。安装完探针工具后只刷新对应状态，模块勾选、工具链选择和清单滚动位置都应保留。

## 实现与评审约定

沿用上游 TypeScript 命名、Lit 组件和 VS Code 接口；新增函数按一个动作拆分，通常控制在 50 行执行代码以内。导航负责定位，组件负责展示，扩展宿主负责校验上下文并运行命令。CMakeCache、模块声明和 runner 元数据各复用已有读取器。编译器、目标板与模块参数显示官方名称，并标明来自环境、构建缓存还是本次输入。主题颜色、圆角、焦点环和控件间距在共享样式中维护。每个功能提交应能单独说明用户入口、行为变化和验证方式。

## 此前约定的模块管理行为

- 搜索默认按模块名模糊匹配，正则表达式由用户主动开启。添加仓库时提示每行一个，接受 Windows、Linux 换行，清除每行前后空白，忽略空行。
- 已勾选在上、待勾选在下，各有标题、数量、分隔线和独立滚动区域。模块行显示谁依赖它、清单目标版本、下载状态，以及手动选择或自动识别的理由。
- 已下载且一致、已下载但不一致、未下载、远端未检查分别显示图标与文字，使用主题颜色。单项操作在行内，批量操作在已勾选区标题，工作台导航始终提供模块入口。
- Git 模块与二进制组件使用一致的清单交互。Git 对比清单版本，二进制文件对比模块声明的 SHA-256。一个模块内所有文件都校验通过，才显示已获取。
- HC32F4A0 用作回归示例，实际依赖来自所选 Zephyr 工程和板。模块自动下载可在扩展设置中开启；默认允许先在离线环境检查。手动排除的依赖在同步时也应被尊重。
- 源码、翻译的上游评审和本次工作台开发有各自的分支。工作台提交按功能组织，面向上游的新提议单独讨论。来源节点见 [NOTICE](../../NOTICE)。

复核入口：`npm run compile`、`npm run lint`、`npm run esbuild`、`npx vscode-test --label unit`。在已安装 west 与 PyYAML 的解释器中运行 `python -m unittest discover -s src/test -p "test_west*.py"`，可使用临时本地 Git 仓库复核依赖识别。真实构建需要测试者提供对应的板、模块与编译器。

## 配置页的操作边界与验收

| 页面 | 用户在这里完成什么 | 验收方式 |
| --- | --- | --- |
| 主机工具 | 核对系统包管理器、定位缺失工具并安装 | 常用工具各占一行，状态同时有文字和图标。检查完成后收起无事可做的安装操作。 |
| 工作区 | 确认当前清单与环境，调整 west 更新选项 | 选项直接写入当前 VS Code 工作区，与实际更新命令读取同一设置。已初始化时只在维护区提供重置类操作。 |
| west Git 模块 | 搜索、勾选、下载，核对清单版本 | 已选在上，待选在下。分页只作用于待选列表；筛选、翻页都保留已选项。单项和批量下载入口均可见。 |
| CMake 工程 | 从本地 Zephyr 枚举开发板与 CPU，选择构建目标 | 输入部分板名或 CPU 即可筛选，所选 BOARD 就地显示在选择按钮旁。手填参数原样保留，手填同名项优先，并显示生效值。 |

通用操作优先采用 VS Code 的编辑、删除、前后翻页图标，并提供键盘焦点和中英文名称。下载、更新、初始化等影响工程的动作保留动词。工具栏按控件整体换行；可变长度的路径允许换行或通过提示查看。短清单按内容展开，长清单在自身区域浏览。共享宿主命令、配置存储和搜索算法，各页自行管理交互状态。
